# Architecture

> Status: **current as of release 2026.11.4 (2026-11-27)**. Research prototype; results and open problems: [OVERVIEW.md](OVERVIEW.md). Local mock layout: `deploy/local/`; Phala specifics: [PHALA.md](PHALA.md). Facts about dstack are from dstack v0.6.6 (commit
> `c873038`, 2026-11-20); see [DECISIONS.md](DECISIONS.md) for sources.

## 1. Overview

```
 user machine                     dstack gateway CVM            app CVM (Intel TDX, dstack OS)
┌──────────────────┐            ┌─────────────────────┐        ┌──────────────────────────────────────────────┐
│ attested-vw-     │  TLS 1.3   │ TLS *passthrough*   │  WG    │ proxy (Caddy)  ── TLS terminates HERE        │
│ verify           │──────────▶ │ routes on SNI only, │──────▶ │   │  key generated in-CVM, ACME from in-CVM  │
│                  │            │ never sees plaintext│        │   ├── /                     → vaultwarden:80  │
│ Bitwarden apps / │            └─────────────────────┘        │   └── /.well-known/tee-attestation → attest  │
│ browser          │                                           │                                              │
└──────────────────┘                                           │ vaultwarden (upstream image @sha256)         │
                                                               │   /data on CVM encrypted disk                │
                                                               │ attest (sidecar)                             │
                                                               │   reads Caddy cert store (read-only)         │
                                                               │   asks guest agent for quote ──▶ dstack.sock │
                                                               └──────────────────────────────────────────────┘
```

All three containers are services in one `docker-compose.yml`, wrapped by
dstack into `app-compose.json`, whose SHA-256 is extended into RTMR3 as the
`compose-hash` event before any container starts.

## 2. TLS termination: the critical decision

C4 in the threat model ("the TLS key is held by the attested guest") only
means something if the TLS session the user sees terminates inside the app
CVM. dstack offers three relevant routing modes (dstack docs,
`docs/dstack-gateway.md#url-format`):

| Mode | Who holds the TLS key the user sees | C4 possible? |
|------|-------------------------------------|--------------|
| Gateway default `https://<app_id>[-<port>].<base_domain>` | **dstack-gateway CVM** (terminates, forwards plaintext over WireGuard) | No, not for our CVM. Only "some attested gateway" (Phala's `/.dstack/acme-info` evidence). |
| Gateway passthrough `<app_id>-<port>s.<base_domain>` or a custom domain with TXT `_dstack-app-address.<domain> = <app_id>:<port>` | **Our app CVM** (gateway routes raw TCP by SNI) | **Yes.** |
| dstack-ingress (HAProxy + certbot in the app CVM, custom domain) | Our app CVM | Yes, but its own evidence (`/evidences/`) binds neither a nonce nor the TLS key, so we would still need our sidecar. |

**Choice: raw TCP to Caddy inside the app CVM.** Self-hosted dstack: the host
maps port 443 straight to the CVM (`vmm-cli deploy --port tcp:0.0.0.0:443:443`,
no gateway, D-031). Phala Cloud: gateway TLS passthrough on a custom domain.
Rationale:

* The private key is generated by Caddy inside the CVM and never leaves it;
  the gateway sees only ciphertext, so it is in the availability path but not
  the confidentiality or integrity path.
* Caddy can obtain a publicly trusted certificate with **TLS-ALPN-01**, which
  works over SNI passthrough with no DNS API token inside the CVM. (dns-01, as
  used by dstack-ingress, would need a DNS credential injected through the
  *unmeasured* encrypted env.) Confirmed on the live Phala runs: passthrough
  forwards the `acme-tls/1` ClientHello untouched (D-043).
* We need our own sidecar anyway (nonce + SPKI binding), so a second proxy
  stack (HAProxy + certbot) buys nothing.
* Fallback if TLS-ALPN-01 through the gateway fails: the gateway's
  `<app_id>-443s.<base_domain>` name with a certificate issued for it, or
  dns-01 with a narrowly scoped token (documented as operator-controlled).

**CAA with `accounturi`** (done for the demo name on 2026-11-27, D-052):
a CAA set pinned to the in-CVM ACME account (dstack-ingress does this with
`SET_CAA=true`), so that a certificate for the name cannot be obtained from
another account or CA without a visible DNS change. A name that is a CNAME
can hold no other records, and a CAA lookup at it follows the CNAME, so the
name must be an **A record** to the gateway (cost: the gateway's address is
copied into the zone and must be updated if Phala moves it). The demo name
has `issue "letsencrypt.org; accounturi=…/acct/4048885521;
validationmethods=tls-alpn-01"` and `issuewild ";"`; Caddy renewed under it.
A wildcard `*.parent` also covers the name, and its issuance follows the
*parent's* CAA set, so the parent needs one too. `example.com` has
`issuewild ";"` at its apex since 2026-11-27 (it also forbids wildcard
certificates for every other name of the zone without its own CAA set),
and `demo/live/caa-check.sh` passes on both lines. In every case the DNS
operator can change CAA: it is a tripwire together with CT, not a barrier
against the operator.

CT monitoring is implemented: `demo/live/ct-check.sh` checks that every
logged certificate valid for the name, including `*.parent` wildcards, has
an attested key (Cert Spotter's `pubkey_sha256` against the SPKI hashes in
verifier PASS outputs). It is a script run by hand, not a monitor. On
`vault.example.com` it fails until 2027-01-31: Cloudflare's `*.example.com`
certificates, issued before Universal SSL was turned off for the zone
(D-048, D-052).

## 3. Attestation flow

```
verifier                                          app CVM
   │ 1. TCP+TLS to vault.example.com (WebPKI) ───▶ Caddy
   │    capture leaf cert, spki = SHA-256(SPKI DER)
   │ 2. nonce ← 32 random bytes
   │    GET /.well-known/tee-attestation?nonce=…   (same TLS connection)
   │                                         ───▶ Caddy ──▶ attest
   │                                                attest: read current leaf from Caddy storage
   │                                                        spki' = SHA-256(SPKI DER)
   │                                                        rd = SHA-512(tag ‖ nonce ‖ spki')
   │                                                        quote ← guest agent GetQuote(rd)
   │ ◀── JSON {quote, event_log, nonce, spki_sha256=spki', app_compose, …}
   │ 3. verify quote (dcap-qvl + Intel PCS collateral): signature, TCB, debug off
   │ 4. check spki' == spki, nonce echo, report_data == SHA-512(tag ‖ nonce ‖ spki)
   │ 5. MRTD, RTMR0-2 == policy; replay event_log (digests recomputed)
   │    → RTMR3 == quote.RTMR3; compose-hash event == policy.compose_hash
   │    and == SHA-256(served app_compose bytes)
   │ 6. parse docker_compose_file from app_compose; every image @sha256 and allowlisted
   │ 7. report ✓/✗, exit code
```

Note in step 4: the verifier's own `spki` (from its handshake) is what goes
into the recomputation. `spki_sha256` in the response is only compared for a
clearer error message.

### Certificate rotation race

Caddy renews certificates (by default when about a third of the lifetime
remains). If a renewal happens between the verifier's handshake and the
sidecar reading the store, the SPKI differs (Caddy generates a new key per
certificate unless configured to reuse it). The verifier fails closed with a
specific message and may retry once on a new connection. The sidecar also
scans for the single leaf matching the configured domain; more than one
candidate is an error.

## 4. Components

### 4.1 `vaultwarden`

Upstream `vaultwarden/server@sha256:<digest>` (from Docker Hub or GHCR).
Hardened configuration, **all literal in the measured compose** (encrypted
env values are not measured, see §5):

| Variable | Value | Why |
|----------|-------|-----|
| `DOMAIN` | `https://<domain>` | links, WebAuthn |
| `SIGNUPS_ALLOWED` | `false` | |
| `INVITATIONS_ALLOWED` | `true` | onboarding via org invites |
| `DISABLE_ICON_DOWNLOAD` | `true` | no outbound icon fetches revealing users' sites |
| `ICON_CACHE_TTL` | `0` | required with the above, otherwise cache expires and is never refilled |
| `ICON_SERVICE` | `internal` | an external service redirects the client's browser to a third party |
| `PUSH_ENABLED` | `false` | push goes through Bitwarden's relay (sees device tokens and timing); trade-off: mobile clients sync on open/poll instead |
| `SSO_ENABLED` | `false` | IdP would be outside the TEE |
| `ORG_CREATION_USERS` | `none` | nobody creates organisations; an explicit list would be a new release |
| `PASSWORD_HINTS_ALLOWED` / `SHOW_PASSWORD_HINT` | `false` / `false` | hints are plaintext to the server |
| `LOG_LEVEL` | `warn` | limit request logging (IPs, icon domains) that may be exported by the platform |
| `IP_HEADER` | `X-Forwarded-For` from Caddy, trusted proxies `local` | correct client IPs for rate limiting |
| `ADMIN_TOKEN` | **unset** (DECISIONS D-008) | admin panel = operator access to metadata + runtime config |

`/data` is a named docker volume on the CVM's encrypted disk. No host bind
mounts.

### 4.2 `proxy` (Caddy)

Pinned `caddy@sha256:<digest>`. Caddyfile is embedded in the compose (so it
is measured), routes `/.well-known/tee-attestation` to the sidecar and the
rest to Vaultwarden (WebSocket upgrade passes through on the same port).
Certificate store at `/data/caddy/certificates/<issuer>/<domain>/<domain>.crt`.
Up to release 2026.11.2 that is inside the persistent `caddy_data` volume,
which the sidecar mounts read-only as a whole. From release 2026.11.4
(D-049, D-052) `/data/caddy/certificates` is a separate tmpfs-backed named volume
(`caddy_certs`): certificates and private keys exist in memory only and are
re-issued at every boot (Let's Encrypt: at most 5 identical certificates
per week, so at most 5 cold starts per week); `caddy_data` keeps only the
ACME account. Reason: THREAT_MODEL §1, precondition of C3/C4.

### 4.3 `attest` (sidecar)

Rust, minimal dependencies, single route, `#![forbid(unsafe_code)]`. Mounts:
`/var/run/dstack.sock` and Caddy's certificates read-only (the whole
`caddy_data` up to 2026.11.2; only the `caddy_certs` tmpfs from 2026.11.4).
Runs as uid 0 with every capability dropped, read-only root filesystem and
`no-new-privileges`: Caddy writes its certificate files `0600 root`, so no
other uid can read the leaf. Request size limit and a two-level rate limit
(per client address as reported by Caddy, and global). Never reads `/data`
of Vaultwarden. It can read the TLS private key file (same directory as the
certificate) but never opens it.

Platform behind `QuoteProvider`:

* `Dstack`: guest agent v0 `GetQuote` (`report_data` passed raw, ≤ 64 bytes,
  no hashing by the agent) or v1 `Attest` (MessagePack). See DECISIONS D-004.
* `ConfigfsTsm`: SEV-SNP via `/sys/kernel/config/tsm/report` (stretch; verified in code, **never run on hardware**, see [SNP.md](SNP.md), D-050; `ATTEST_SNP_BINDING=measured-cmdline` for the Servury image, [SNP_SERVURY.md](SNP_SERVURY.md), D-055).
* `GcpCs`: Google Cloud Confidential Space launcher socket; the evidence is
  a Google-signed attestation token whose `eat_nonce` carries `report_data`
  (run live once on 2026-11-27, D-053; trusts Google's attestation service;
  no persistence; see [GCP_CONFIDENTIAL_SPACE.md](GCP_CONFIDENTIAL_SPACE.md), D-051).
* `Mock`: INSECURE, local only.

### 4.4 `verifier`

Library + CLI, runs on the user's machine. Network access only to the target
and to Intel PCS (collateral) / AMD KDS (VCEK chain) / Google's JWKS URL
(`gcp-cs` token signing keys). Unit tests use recorded
fixtures and a pinned verification time.

## 5. What is measured and what is not (dstack)

| Input | Measured? | Where |
|-------|-----------|-------|
| OVMF firmware | yes | MRTD |
| Virtual hardware config, ACPI | yes | RTMR0 (depends on vCPU/RAM, so the policy pins a size) |
| Kernel | yes | RTMR1 |
| Kernel cmdline (incl. rootfs dm-verity root hash), initrd | yes | RTMR2 |
| `app-compose.json` (compose file, pre-launch script, `allowed_envs` names, KMS/gateway flags) | yes | RTMR3 `compose-hash` |
| App ID, instance ID, key provider | yes | RTMR3 events |
| **Encrypted env values** | **no** | operator (or anyone with VMM access) can substitute them |
| Container images | indirectly: the *reference* is measured | pinned by digest *inside* the measured compose; Docker checks the digest when it pulls |
| Docker's image store, containers, networks (on the data disk) | **no** | an image already present is not re-checked against its digest: open finding, THREAT_MODEL §7 (K1). Containers and networks are removed by the measured pre-launch script from 2026.11.4 |
| Contents of `/data` (DB, `config.json`, `rsa_key.pem`), ACME account | no | persistent state; see THREAT_MODEL §1, §5 and R6 |

Consequence: every security-relevant setting goes literally into the compose.
Encrypted env is used only for values whose substitution cannot change
security-relevant behaviour (e.g. SMTP password: substitution breaks mail,
it does not grant access).
