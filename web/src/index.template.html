Attested Vaultwarden: browser verifier

Research prototype. Not production-ready, and a PASS here does not mean "safe for your passwords". It checks less than the command-line verifier; read what this page cannot check.

Enter the domain of an Attested Vaultwarden server. This page asks it for a fresh hardware attestation and checks that the server is a genuine confidential VM (Intel TDX on dstack; experimentally Google Cloud Confidential Space and AMD SEV-SNP) running exactly the selected published release, and that every publicly logged TLS certificate for the name belongs to a key attested inside such a VM.

What is checked

  • Hardware evidence. The Intel-signed TDX quote, against Intel's root certificate built into the verifier, with fresh Intel collateral (revocation lists, TCB info); TCB status as the release policy requires; debug off. Google Cloud Confidential Space releases: there is no hardware quote to see. The evidence is a token signed by Google's attestation service, checked against Google's signing keys, which this page fetches from Google at each run; you trust Google's statement about the VM. AMD SEV-SNP releases (never run against a real deployment): the AMD-signed report and its VCEK certificate, against AMD's root certificates built into the verifier.
  • Freshness. The quote signs a random nonce this page generated a moment ago.
  • Software. Firmware and OS measurements equal the release policy; the runtime event log replays to the quoted RTMR3; the measured compose hash equals the policy and the SHA-256 of the compose document the server shows; images are pinned by digest and allowlisted; no launch scripts or injected settings beyond what the policy pins.
  • TLS key, via Certificate Transparency. The quote also signs the hash of the server's TLS public key. This page then lists every certificate that is currently valid for the name in the public CT logs (including wildcard certificates of the parent domain) and requires each one's key to be the key attested just now, or one attested earlier and bundled with this page. If this is the only line that fails, the VM itself verified, but somebody outside it holds a certificate that browsers accept for the name; the list under the result shows which. The usual case is a wildcard (*.example.org) held by a CDN or DNS provider of the parent domain. The demo deployment vault.facundo.dev fails here for exactly that reason: Cloudflare wildcard certificates for *.facundo.dev, issued before Cloudflare's certificates were turned off for the domain on 2026-11-27, stay valid until they expire (the last one on 2027-01-31). Use the command-line verifier for a per-connection check in the meantime.

What this page cannot check

  • It does not see your connection's certificate. Browsers do not show a page the TLS certificate of its own connection. The command-line verifier checks that the very connection it is on ends inside the attested VM; this page cannot, and never prints that check. The Certificate Transparency check replaces it: if every valid logged certificate for the name has an attested key, a browser that enforces CT can only reach an attested VM under this name.
  • Detection, not prevention. A certificate issued minutes ago may not be in the logs or in the monitor's index yet. An attacker with control of the domain has that window. Re-run later, or watch the name with a CT monitor.
  • Cert Spotter is trusted to return every logged certificate for the name. This page cannot check that the list is complete, and it queries no second monitor.
  • Old attested keys still count. A key attested in the past stays accepted while its certificate is valid, even if the VM that held it has been replaced. Revocation is not considered.
  • Collateral comes from a mirror. Intel's own service does not allow requests from web pages, so collateral is fetched from Phala's PCCS mirror (pccs.phala.network). It is signed by Intel and verified here; the mirror is trusted only to be available and reasonably fresh.
  • Confidential Space: Google's key list is taken on trust. Nothing signs the key list itself; the page relies on the browser's TLS connection to googleapis.com, as the command-line verifier relies on its own.
  • Who served you this page? Whoever controls the page controls the answer. Use a copy you built yourself or got from a source you trust; do not trust a copy served by the server being checked. The command-line verifier remains the reference.
  • Your Bitwarden apps check none of this. A PASS says what the server at this name runs now. It does not make the apps verify anything, and it does not fix weaknesses in the published code itself.

What this page contacts

  • The domain you enter (/.well-known/tee-attestation), which must allow cross-origin reads; releases before 2026.11.3 do not, and fail here with a message saying so.
  • pccs.phala.network for Intel collateral (TDX releases).
  • www.googleapis.com for Google's attestation signing keys (Confidential Space releases).
  • kdsintf.amd.com for the VCEK certificate (SEV-SNP releases, only if the server did not send it).
  • api.certspotter.com for the certificate list (it learns the domain you check; unauthenticated requests are rate limited).
  • hub.docker.com, display only: to show which tags point at the pinned image digests. Docker Hub usually refuses requests from web pages, in which case the line says the lookup failed. It never affects the result.

No cookies or credentials are sent, nothing is stored, and no other script or resource is loaded: the page is one self-contained file.
